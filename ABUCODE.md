# ABuCode

**ABuCode** is a minimal-conflict fork of OpenCode `v2.4.0` layered with MultiCode's full coding-side arsenal—Household 343 persona engine (with visual multi-character picker & wildcards), **Squad** multi-agent workflows (`diagnose` / `review` / `design` / `map` with paired Skeptics & cross-subscription cost routing), Household `dispatch_subagent`, proactive repo context pre-injection, `.env.local` provider vault, Poe/XML stream bridge + loop circuit breaker + Poe title thrift, GMT+8 `zzz_local/Chat-History` Markdown archiver, Pinned Session Memory compaction, quote/subshell-aware 4-tier security bodyguards + a DNS-checked SSRF shield on the agent's fetches and their redirect hops, guards that keep the agent off the engine's own server, password and database (within the limits in their section), 18-action `playtest_url` with port reuse, custom bubble styling, and `Alt+Space` Desktop summon (with busy-hotkey fallback & tray approval alerts)—across **both** the Terminal CLI/TUI and the Dedicated Desktop/Web GUI.

## Running ABuCode

All modes connect to the same isolated `abucode` local background engine and SQLite store (`~/.local/share/abucode` / `~/.config/abucode`), leaving stock `opencode` and `MultiCode` completely untouched:

* **Terminal CLI / TUI (Windows):** `.\abucode.cmd [project-path]` *(or `node packages\cli\bin\abucode.cjs`)*
* **Terminal CLI / TUI (macOS/Linux):** `./abucode.sh [project-path]`
* **Web GUI:** `.\abucode_web.cmd` *(or `bun run dev:web`)*
* **Dedicated Desktop App (Electron + Tray + `Alt+Space` Summon):** `.\abucode_desktop.cmd` *(or `bun run dev:desktop`; pass `-- --minimized` to start hidden in tray)*

## Experimental features

OpenCode turns most of its experimental features on in anything run from source, which is how ABuCode runs. The launchers (`abucode.cmd`, `abucode.sh`, `abucode_desktop.cmd` and `packages/cli/bin/abucode.cjs`) therefore start the engine with those switched off, by putting this in `OPENCODE_FLAGS`:

```
-full_codemode,-home_memory,-project_overlay,-machines,-media_blob,-artifacts,-sqlite_fts,-console_watches,-recommended_api,-opencode_api
```

`packages/schema/src/config/flag.ts` says what each one does. They stay off because ABuCode's guards were not written for them. Full Code Mode, for one, gives the model's scripts file access that does not pass through the secret-file guard.

* **To try one,** name it in `OPENCODE_FLAGS` before you start ABuCode: `$env:OPENCODE_FLAGS = "artifacts"` in PowerShell, `set OPENCODE_FLAGS=artifacts` in cmd, or `OPENCODE_FLAGS=artifacts ./abucode.sh`. The launcher puts your entries after its own, and a later entry for the same feature wins. `all` does not override the list.
* **`experimental.<name>: true` in a config file does not turn a listed feature on,** because `OPENCODE_FLAGS` outranks config.
* **The engine reads the flags once, when it starts, and the terminal launcher reuses an engine that is already running.** An engine started any other way, or before the launchers had this list, keeps its own flags. Run `.\abucode.cmd service stop` once after updating, after any `bun run dev`, and before changing flags.
* **Do not set `OPENCODE_FLAGS` with `service set env`.** A saved value replaces the launcher's list, which turns every feature it does not name back on.
* **Only the launchers do this.** `bun run dev` and `bun run dev:desktop` carry no list, so an engine they start has the default-on features on. That includes the desktop app on macOS and Linux, which has no launcher. A WSL server added inside the desktop app does not get the list either. `abucode_web.cmd` and `bun run dev:web` start no engine of their own.
* **After merging a newer OpenCode, or editing a launcher,** run `bun run script/test.ts test/abucode-launchers.test.ts test/plugin/abucode-guard.test.ts test/plugin/abucode-config-edit.test.ts test/plugin/abucode-engine-self.test.ts ../server/test/abucode-server-address.test.ts` in `packages/core`. The first file fails if the release added a feature the launchers do not yet switch off: add it to the list in all four and in the block above. The next two fail if the merge drops the ABuCode id from the protected list, removes the reserved-id check, changes how file edits ask for permission, renames core's unattended marker, moves the system config folder, or renames the shell tool or its `command` and `workdir` fields (next section). They do not check that `OPENCODE_CONFIG` still names the config file. The last two fail if the merge stops the server from recording the address it listens on and its password, drops the request check in Code Mode's `fetch`, or changes how the `webfetch` tool, Code Mode's `fetch`, their redirect hops, `playtest_url`, file reads and shell commands ask for permission, or how plugins see each model request (section after next).

## The ABuCode plugin cannot be switched off from config

ABuCode's server plugin, `abucode.core`, enforces the policy tiers and the secret-file and network guards. A `plugins` entry that would remove it (`"-abucode.core"`, `"-abucode.*"` or `"-*"`) is ignored in every config file, your own `~/.config/abucode/opencode.json` included, and the engine does not say that it ignored one. The same plugin carries the personas, memory, archiver and provider vault, so no config entry gives a stock OpenCode run from this checkout.

* **A plugin loaded from config cannot take its id either.** The engine does not activate such a plugin and lists it as failed with "Plugin ID abucode.core is reserved for a built-in plugin". Its code is still imported to read the id.
* **The agent asks before it edits engine config.** That is any file named `opencode.json` or `opencode.jsonc`, anything in a `.opencode` folder, anything in the global config folder (`~/.config/abucode`, or `OPENCODE_CONFIG_DIR` when set) or the system config folder, and the file `OPENCODE_CONFIG` names. Theme and doc files in those places count too. An edit to them by a file tool waits for your approval in every Policy tier, even where your permission rules allow it; a rule that denies the edit still denies it. Links to files and folders that already exist, and other spellings of them, are followed. The Plan agent's `~/.opencode/plan` folder is left out, except for an `opencode.json` or a `.opencode` folder inside it.
* **In unattended work, such as an automation run, such an edit is refused.** Nobody is there to approve it, so the edit fails. The experimental home memory's daily skill upkeep (on under `bun run dev` and the desktop app on macOS and Linux) does not count as unattended: its skill edits wait for approval in a session you do not see.
* **Auto-approval answers this prompt like any other.** `run --auto`, the terminal's auto-accept mode and the app's auto-approve setting approve it without showing it to you.
* **Choosing Always in that prompt does not stop the next one.** As on any edit prompt, it also saves an allow for every other file edit in this project's sessions, including files outside the project folder.
* **The agent's shell commands also ask, in every Policy tier, when they visibly write those files.** That covers the agent's shell tool and `playtest_url`'s `start_command`: output redirection (`>`, `>>`, `>|`, `>& file`), `tee`, `cp`, `mv`, `install`, `ln`, `touch`, `sed -i` and `perl -i`, `dd of=`, `curl -o` and `wget -O` or `-P`, and archives unpacked with `tar` or `unzip`, also inside `sh -c`, `eval`, `$(…)` and `xargs`. On Windows, PowerShell's write cmdlets and their usual aliases count too. Each file is resolved against the folder its command runs in, after the shell tool's `workdir` and any `cd`, and a download or unpacked archive into a config folder counts. `~`, `$HOME` and other variables in file names are expanded from the engine's own environment. The prompt names the files (the app also shows the command), it offers no Always that sticks, and where the Policy tier asks about the command too, a second prompt follows.
* **What this does not cover.** A shell command that builds the file name at run time, or runs a script or program that writes the file itself (`python -c`, `node -e`, `git checkout`, PowerShell's `[IO.File]` methods), runs as the Policy tier allows, which outside Request Review usually means without asking. So does a shell command an automation runs as its action, and deleting those files with `rm` (which the Default and Auto tiers ask about anyway). Code the engine runs from elsewhere, such as a plugin your config points to outside those folders or a program the engine starts, can still be changed without this prompt. A repository you open can still ship plugin code of its own, as OpenCode allows, and code that runs inside the engine is not held by the guards.
* **Two of these protections are edits to upstream files** (`packages/core/src/plugin/internal.ts` and `packages/core/src/plugin/supervisor.ts`), which a merge can drop. The post-merge command above runs the tests that catch that.

## The agent is kept off the engine's own server, password and database

The engine's API answers to the password it keeps on disk, and with it a request can run any command and answer the agent's own permission prompts. The database holds every session and the Policy tier. So ABuCode keeps the agent away from all three, within the limits listed at the end:

* **The URLs the agent fetches pass the address check.** That is the `webfetch` tool, Code Mode's `fetch`, each redirect hop of both, image downloads, and the URLs handed to video generation. A request to the engine's own server is refused, by any method and to any path: the address it listens on (also as `localhost`, another loopback spelling, this machine's network addresses, or a name that resolves to one of them), the managed service's address recorded in the state folder, and the remote-access URL while remote access is on. `playtest_url` refuses it too: its target and `goto` steps are checked, and its browser connects only through a local proxy that refuses the engine's address, so everything the page loads is checked, redirect hops, WebSockets, workers and prefetched or prerendered pages included. That browser reaches only loopback servers, and public ones with `allow_external_assets`, and the play-test stops before it opens the page if the browser does not use the proxy (a browser policy can set its own). The report lists the connections the proxy refused. Cloud-metadata and reserved addresses are refused, as are names that do not resolve and anything but `http://` and `https://` URLs. GETs to a dev server on another port still work, which `playtest_url` and local docs rely on.
* **Code Mode's `fetch` asks before anything but GET and HEAD to this machine or the local network.** The `webfetch` tool only ever GETs. A redirect hop cannot ask, and nobody can answer in unattended work, so there such a request is refused.
* **The file tools refuse the engine's state files.** Those are the service files in the config and state folders (`service-local.json`, or `service.json` and `service-<channel>.json` for other channels) and the database in the data folder (`opencode-local.db` and its `-wal` and `-shm` files, or the file `OPENCODE_DB` names), wherever `XDG_*`, `OPENCODE_CONFIG_DIR` or `ABUCODE_CONFIG_DIR` put those folders. Links, hard links and other spellings are followed. A content search of a folder at or above them is refused too, the home folder included, because the search reads hidden folders: search a folder below it instead. The read tools of Squad and Household subagents (`run_workflow`, `dispatch_subagent`) refuse them the same way.
* **A shell command that names them waits for approval, in every Policy tier but Turbo,** and is refused in unattended work. ABuCode reads the command whole, with the folder it runs in, so a `cd` or the shell tool's working folder counts, and a command run inside a state folder counts whatever it names. That covers the file by path in the usual spellings (`~`, `$HOME`, `$XDG_STATE_HOME`, quoting, brace lists, globs), its path inside inline code or a heredoc such as a `python3 -` script, a state folder or a folder above one inside the home folder named in an interpreter's code (which can move or read it whole), and a folder at or above them given to a command that reads, copies, moves or links folders whole, such as `grep -r`, `tar`, `cp -r`, `mv` or an interpreter's script, also behind a launcher such as `caffeinate` or `uv run`, or to a container as a bind mount, and all of this also inside `sh -c`, `eval`, `emulate -c`, `$(…)` and a script a shell reads from a heredoc or a here-string. `playtest_url`'s `start_command` is read the same way, in its `cwd`, and so is an automation's shell command when the automation is made. Where the Policy tier asks about the command too, a second prompt follows; an automation's one prompt gives both reasons.
* **The engine's password is masked in every tool result and in everything else the model reads,** such as a background command's output, which arrives later as a message, and what subagents send to their model. It is masked as the service files hold it, or as the server took it from `OPENCODE_PASSWORD`, and as a Basic credential or an `auth_token` carries it, so a read the checks above miss does not hand it to the model as written. A password under 8 characters is masked only in its credential forms. The provider keys of the `.env.local` vault are masked the same way. A command that prints a process's environment (`ps -E`, `/proc/<pid>/environ`) waits for approval in every tier but Turbo.
* **What this does not cover.** A file name the command builds at run time or receives through a pipe or a variable, a program that finds the files by itself, a command that re-encodes what it reads, and globbing that a shell's startup files change, run as the Policy tier allows. When a compaction has to send the history as text, part of it is rebuilt from storage after the mask runs, so the model that writes the summary can see a password or a vault key a command printed; the agent's own requests stay masked. Requests made by shell commands, the browser tools and MCP servers do not pass the address check, nor does a name whose address changes between the check and the request, nor a redirect an image download follows. On a network that resolves names only through a proxy, or answers every name with a placeholder address, a URL with a name is refused. Code Mode's in-process `opencode:` URLs (the opt-in `opencode_api` feature, which the launchers keep off) reach the API with no permission check at all.
* **Two of these protections are edits to upstream files:** the server records the addresses it listens on and its password in `packages/server/src/process.ts`, which the plugin cannot import, and Code Mode's `fetch` in `packages/core/src/codemode/fetch.ts` passes on only a request's method, headers and body, and checks each redirect hop with the method it is sent with. The post-merge command above runs the tests that fail if a merge drops them.

## MultiCode ↔ ABuCode Native Surface Equivalence Ledger

Several everyday coding workflows exist in **both** MultiCode and ABuCode, **but look different** because MultiCode is a bespoke single-page FastAPI web app with a custom right-hand Control Center rail, whereas ABuCode intentionally uses **OpenCode `v2.4.0`'s first-class native GUI + TUI surfaces** wherever OpenCode already owns the capability (keeping upstream OpenCode merges clean).

Full architectural breakdown lives in `zzz_local/Decisions/Closed/0001-multicode-vs-abucode-native-surface-equivalence.md`:

| MultiCode UI Control | ABuCode Native Surface (GUI & TUI) | How They Work Similarly & Why They Look Different |
| :--- | :--- | :--- |
| **`⚡ Act` / `📋 Plan` button** | **`Build` / `Plan` Agent Switcher** (`Tab` key or composer agent pill) | Both toggle between full read/write execution and read-only planning. ABuCode uses OpenCode's extensible Agent system rather than a hardcoded two-state toolbar button. |
| **`⏪ Undo Turn` / `🌿 Branch` / `✏️ Edit`** | **`/undo`, `/redo`, Timeline Revert & Session Fork** | Both roll back unwanted turns and fork mid-conversation. MultiCode restores saved `before_content` strings only for its file tools; ABuCode uses OpenCode's Git snapshot tracker + SQLite event store, reverting **both** file-tool and shell-command changes with full `/redo`. |
| **`@file` Popup & `📎` Attachments** | **Native `@` Mention Menu & Attachment / Clipboard Paste** | Both fuzzy-match repo files and send images/code to multimodal models (with automatic image-stripping fallback on text-only models). ABuCode's `@` menu also resolves symbols, agents, and MCP resources. |
| **`Appearance` & `Notifications` Modals** | **OpenCode Appearance/Notification Settings + `Settings -> ABuCode`** | OpenCode owns semantic light/dark themes, fonts, and completion sounds across GUI and TUI; ABuCode adds MultiCode's per-bubble color pickers, width presets, and hidden-window tray approval balloons. |
| **Right-Rail `Repository` Dropdown** | **Multi-Project Workspace Tabs, Worktree Picker & `abucode <path>`** | MultiCode switches one `active_repo` at a time; ABuCode keeps multiple repos and **Git worktrees** open concurrently across tabs and TUI sessions, plus adds **LSP**, **MCP**, **integrated terminal tabs**, and **background automations**. |
